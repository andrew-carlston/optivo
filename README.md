# Optivo

WFM/HR SaaS platform for contact centers — realtime monitoring, scheduling, forecasting, attendance & points, staff planning, and cost planning.

## Tech Stack

| Layer | Technology |
|-------|-----------|
| Database | Neon Postgres (serverless, per-company branching) |
| ORM | Drizzle (typed schema, migrations) |
| Framework | Next.js (App Router, server actions) |
| Auth | Neon Auth (Google/Microsoft SSO, stored in your DB) |
| Language | TypeScript (frontend + backend + workers) |
| Styling | SCSS with CSS variable theming |

## Quick Start

```bash
# Install
npm install

# Set up environment
cp .env.example .env.local
# Add Neon DATABASE_URL (from Neon dashboard or `npx neonctl connection-string`)

# Generate + apply migrations
npx drizzle-kit generate
npx drizzle-kit migrate

# Run dev server
npm run dev

# Run a worker
npx tsx src/features/realtime/worker/index.ts
```

## Project Structure

```
src/
  app/                    Next.js routes
    (auth)/               Login, callback (no company context)
    [company]/            All company pages (slug-based routing)

  features/               Self-contained feature modules
    core/                 Shared hooks, components, actions
    auth/                 Authentication & authorization
    hr/                   Employees, departments, org structure
    directory/            Agent profiles, columns, custom fields
    realtime/             Live agent/queue monitoring + consumer worker
    attendance/           Points, warnings, disputes + checker worker
    schedule/             Shifts, templates, calendar + sync worker
    forecast/             Demand forecasting + model runner worker
    staffing/             Headcount planning, capacity
    cost/                 Budgets, labor models, overtime
    analytics/            Reports, dashboards, metrics

  db/
    schema/               Drizzle schema (one file per Postgres namespace)
    migrations/           Generated by drizzle-kit
    client.ts             Neon connection + Drizzle instance

  components/ui/          Shared component library
  styles/themes/          Theme CSS variables
  lib/                    Utilities, helpers
```

## Database Namespaces

Each module uses its own Postgres schema for clean separation:

```sql
core.*          — Companies, users, config, audit, notifications
hr.*            — Employees, departments, divisions, positions
directory.*     — Agent profiles, columns, system connections
realtime.*      — Agent states, queue metrics, status mappings
attendance.*    — Log, points, config, first_seen, disputes
schedule.*      — Shifts, templates, calendar tokens
forecast.*      — Models, predictions, scenarios
staffing.*      — Plans, headcount, capacity
cost.*          — Budgets, rates, labor models
analytics.*     — Reports, saved filters, agent metrics
system.*        — Integrations, feature flags, jobs, API keys
```

## Multi-Tenancy

Each company gets its own Neon database branch:

```
main (shared schema, no data)
  ├── lawnstarter (LS data + any custom tables)
  ├── acme-corp (their data)
  └── company-3 (their data)
```

- Physical data isolation (no RLS needed for tenant separation)
- Company-specific tables/features via branch-only migrations
- Middleware resolves company slug → Neon branch connection
- Schema changes on `main` propagate to all branches

## Feature Modules

Each feature is fully self-contained:

```
features/attendance/
  hooks/            React hooks (usePointsConfig, useAttendance)
  components/       UI (PointsTable, WarningsView, InfractionsTable)
  actions/          Server actions (Drizzle queries, mutations)
  worker/           Background process (attendance checker, cron)
```

Workers run as standalone TypeScript processes:
```bash
npx tsx src/features/realtime/worker/index.ts    # Long-running consumer
npx tsx src/features/attendance/worker/index.ts   # Cron every 5 min
npx tsx src/features/schedule/worker/index.ts     # Cron twice daily
```
